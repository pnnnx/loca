# loca — состояние проекта и задача для следующей сессии

Скопируйте этот файл (или его путь) в новый чат первым сообщением.

## Что это

`~/Documents/loca` — терминальный агент для кода поверх Ollama, аналог Claude Code, чистый Python,
без зависимостей. Машина: MacBook Air, 8 ГБ. Модель по умолчанию в `~/.loca/config.json` —
`qwen3.5:4b`, num_ctx 16384 (профиль 9b лежит рядом в `config.json.9b`: 9b на 8 ГБ впритык).
Запуск: `loca` (обёртка `~/.local/bin/loca` → `python3 -m loca` из репозитория), из Vim — `:Loca`.

## Что уже сделано (не переделывать)

- **Цикл агента** `loca/agent.py`: tool calls → результаты → повтор; сжатие контекста в два этапа;
  защита от зацикливания; субагенты двух типов (`research` — только чтение, `code` — полный набор),
  у них общий контейнер переменных с родителем.
- **Инструменты** `loca/tools/`: `read_file`, `read_symbol`, `repo_map`, `edit_file` (нечёткий поиск
  с выравниванием отступов), `write_file`, `list_dir`, `glob`, `grep`, `bash`, `run_tests`,
  `plan_write`, `run_plan`, `task`, `exit_plan_mode`, `set_var`/`get_var`/`del_var`, `web_fetch`,
  MCP-инструменты.
- **Разбиение задачи — граф подзадач** (заменил плоский `todo_write`, его больше нет):
  - `loca/plan.py` — узел (`id`, `title`, `files`, `depends_on`, `accept`, `result_var`, статус,
    попытки), валидация (висячие зависимости, циклы, дубли id, обязательная приёмка, максимум 8
    подзадач), готовность по зависимостям, отрисовка деревом, сериализация в сессию.
  - Приёмка только исполняемая: `tests` (прогон тестов), `cmd` (код возврата 0), `symbol`
    (в файле появилось определение). Текстовых критериев нет намеренно: 4B в роли судьи своей
    работы всегда отвечает «да».
  - `loca/executor.py` — исполнение: предпроверка приёмки (зелёная до работы → критерий пустой,
    подзадача блокируется), `code`-субагент с контрактом (файлы, что сделали зависимости, карта
    символов, текст приёмки), реальный прогон приёмки, при провале откат снимками и повтор
    (`plan_max_attempts`), после последней попытки — откат и возврат к планированию.
  - Цикл ведёт Python, а не модель: родитель вызывается на планирование и на разбор провала.
    Это экономит его контекст и не выбивает KV-кэш Ollama чередованием промптов.
  - Перепланирование — повторный `plan_write` целиком; подзадачи с теми же `id`+`title`, уже
    прошедшие приёмку, сохраняют статус.
  - Пороги в конфиге: `plan_min_nodes` (3), `plan_min_files` (2), `plan_max_attempts` (2),
    `max_plan_subagents` (12), `plan_rollback`, `accept_timeout`, `plan_outline_files`.
- **Переменные** `loca/state.py`: `set_var` + подстановка `{{имя}}` в аргументы инструментов,
  переживают сжатие контекста и сохраняются в сессии.
- **Тесты** `loca/tools/tests.py`: `run_tests` с автоопределением (pytest/npm/cargo/go/make), нудж
  «изменил код — прогони тесты», нудж про незакрытые подзадачи плана.
- **Хуки** `loca/hooks.py`: `after_edit` (`{file}`), `after_tests`, `stop`.
- **Снимки и `/undo`** `loca/snapshots.py`: копия файла перед каждой правкой, журнал, откат;
  плюс `mark()` / `rollback_to()` — откат целой подзадачи. Неудавшийся вызов `edit_file`
  снимок больше не оставляет, поэтому `/undo` на него не тратится.
- **Точечный think**: размышления на первом шаге хода и после ошибок (`think_smart`).
- **Бенчмарк** `bench/`: 16 задач в двух группах — `core` (12 прежних) и `hard` (4 многофайловых,
  `--tasks hard`). У hard-задач есть **частичные цели**: раннер считает `3/5` подцелей, потому что
  на 4B голое «не прошло» не показывает прогресса. `--verify-tasks` проверяет, что и checks, и все
  частичные цели падают до работы агента.
- **Тесты проекта**: `tests/test_loca.py`, 55 штук, `pytest -q`, поддельные Ollama и MCP-сервер.

Подробности — в `README.md` (разделы «Разбиение задачи…», «Навигация по коду», «Хуки»,
«Откат правок», «Точечные размышления», «Мини-бенчмарк»).

## Разбор прогона от 18.09 и что из него сделано

Прогон `--tasks hard` на `qwen3.5:4b`: 2/4, частичных целей 12/16, две задачи убиты по таймауту
900 c. Главное из него: **`plan_stats.subagents = 0` во всех четырёх задачах** — модель ни разу не
вызвала `plan_write`, то есть весь граф подзадач просто не включался, а многофайловые задачи
решались плоским перебором правок. Плюс убитые по таймауту прогоны не оставляли вообще никаких
метрик (`0/0 токенов`), то есть причину зависания посмотреть было негде.

Сделано по итогам (19.09):

- **План-гейт.** Агент сам требует `plan_write`: сразу, если запрос выглядит многофайловым
  (`looks_multifile`: 3+ путей, «везде / во всём проекте», «переименуй/вынеси» + пара файлов), и
  по ходу — после `plan_gate_steps` шагов (6) с `plan_gate_files` (2) правлеными файлами без плана.
- **Бюджет хода.** `max_seconds` / `--max-seconds`: агент останавливается сам, дедлайн наследуют
  субагенты, исполнитель не берёт новую подзадачу после дедлайна. Раннер передаёт
  `таймаут - --margin` (45 c), так что проверки успевают отработать и результат не теряется.
- **Видимость.** Метрики пишутся после каждого шага; в них добавлены `touched`, `budget_hit`,
  `tool_errors` и трасса последних 60 вызовов. В отчёте у упавшей задачи печатается разбор
  (какие инструменты, доля ошибок, был ли план, последние шесть вызовов).
- **Vim.** Корень проекта больше не уезжает в `$HOME` (виноват был глобальный `~/.loca`),
  добавлена `:LocaRoot`, корень запоминается для терминальных буферов, функция перестала зависеть
  от имени файла плагина (E746).

## Прогон 19.09 после план-гейта: 3/4, целей 15/16

`--tasks hard`, `qwen3.5:4b`: было 2/4 и 12/16 целей с двумя таймаутами — стало 3/4 и 15/16 без
единого таймаута. План заработал: субагентов 6 / 2 / 4 на трёх задачах (было 0 везде).

Единственный «провал», `hard_rename_package`, оказался **багом бенчмарка, а не агента**: loca кладёт
снимки для `/undo` в `LOCA_HOME`, бенчмарк ставил `LOCA_HOME` внутрь рабочей копии, снимок хранит
файл ДО правки — и проверка `! grep -rq calc_total --include='*.py' .` находила старое имя в
`.loca_home/snapshots/00001_core.py`. Трасса это и показывала: собственный `grep` агента давал
`No matches`, а проверка падала. Исправлено: состояние агента вынесено в отдельный временный
каталог, `snapshot()` игнорирует служебные каталоги, проверки с `grep -r` получили `--exclude-dir`.
Регрессия закрыта тестом `test_bench_keeps_agent_state_out_of_workspace`. То есть фактический
результат того прогона — 4/4 по работе агента.

Ещё из трассы: в `hard_rename_package` было 6 вызовов `plan_write` при 2 субагентах — модель
переписывала план по кругу. Добавлены счётчики (`writes`, `rejected`, `refused`) и прямое указание
после четвёртого плана без единой запущенной подзадачи.

## Живой прогон 19.09 (дилемма заключённых) — три бага, все исправлены

Пользователь попросил у loca написать игру; модель дважды отправила один и тот же `write_file` на
`z/dilemma.py` и утонула в двух подряд сжатиях контекста. Разбор:

1. **`write_file` на существующий файл** требовал чтения (это правильно), но сообщение звучало как
   правило, а не как факт. Модель решила «файла нет» и повторила вызов. Теперь сообщение называет
   размер файла, говорит «он существует, не выдумывайте» и диктует следующий вызов; добавлен
   `overwrite=true` как законный выход. Ответ различает `Created` и `Overwrote`.
2. **Детектор цикла ждал трёх** одинаковых вызовов. Теперь два одинаковых *провалившихся* подряд
   дают прямое указание не отправлять третий.
3. **Сжатие контекста раздувало контекст** (~9543 → ~11427) и поэтому срабатывало каждый шаг, каждый
   раз тратя вызов модели. Теперь результат принимается только если он меньше, иначе откат и пауза
   до реального роста контекста (`_compact_floor`).

Плюс под Python 3.14 из brew: код чист (только stdlib, ничего удалённого), но pytest после
обновления питона остаётся у старого интерпретатора — `detect_test_command` теперь проверяет
доступность pytest тому же python и иначе берёт stdlib-unittest, а `looks_broken` считает
`No module named pytest` поломкой окружения, а не провалом субагента.

## Что делать дальше

1. **Снять цифры заново.** `python3 bench/run.py -m qwen3.5:4b --tasks hard --out runs/hard2.json
   --baseline runs/hard-clean.json`. Теперь даже упавшая задача покажет шаги, токены, трассу и
   строку «план не использовался» либо «план: субагентов N». Первое, что смотреть, — заработал ли
   гейт (в `tools` должен появиться `plan_write`/`run_plan`).
2. **Настроить пороги по цифрам.** Если на core-задачах выросли токены и время — поднять
   `plan_min_nodes`/`plan_min_files`. Если hard-задачи упираются в откаты — посмотреть, не слишком
   ли крупные подзадачи планирует модель, и не сделать ли `plan_max_attempts: 3`.
3. **Разобрать типовые провалы.** Частые кандидаты: модель пишет приёмку «прогнать все тесты» на
   каждую подзадачу (тогда предпроверка её блокирует — надо усилить формулировку в описании
   `plan_write`), не указывает `files`, делает подзадачи слишком мелкими.
4. **Отдельная модель для кода** (обсуждалось, не сделано). Теперь это дешевле встроить: исполнитель
   уже отделён, можно роутить подзадачу на `qwen2.5-coder` из конфига. Риск прежний: переключение
   модели в Ollama вытесняет KV-кэш основной. Варианты: резидентный `qwen2.5-coder:1.5b/3b` при
   `OLLAMA_MAX_LOADED_MODELS=2` либо `:7b` пакетно. Решать по бенчмарку.

## Ограничения окружения

- Ollama живёт на macOS: из окружения Claude она недоступна, `ollama pull` и бенчмарк запускает
  человек.
- В контейнере Claude нет pytest (pypi закрыт политикой) — тесты гоняются самодельным shim-ом;
  у человека обычный `pytest -q` в корне репозитория.
- `loca/ui.py`, `loca/__init__.py`, `loca/__main__.py` в контейнере есть, но не менялись: тесты
  гонялись на настоящем `ui.py`, в поставку эти файлы не входят.
- Домашняя папка целиком недоступна: правки `~/.vimrc` и `~/.zshrc` делать нельзя, только через
  `~/.vim/plugin/`, `~/.oh-my-zsh/custom/` и `~/.loca/`.
- Задачи бенчмарка с `unittest discover` обязаны содержать `tests/__init__.py`: с Python 3.11
  каталог тестов должен быть пакетом, иначе discover падает с `Start directory is not importable`.
  Это стерёг тест `test_bench_unittest_tasks_ship_tests_package`.
