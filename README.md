# loca — локальный агент для кода в терминале

Аналог Claude Code, который работает с локальной моделью через Ollama. Написан на чистом Python, без
сторонних зависимостей. По умолчанию — `qwen3.5:9b` (нужно 16 GB; на 8 GB см. раздел про выбор модели).

Как у Claude Code: режим плана с подтверждением (`exit_plan_mode`), субагенты двух типов,
переменные для промежуточных результатов (`set_var`) и обязательная проверка тестами (`run_tests`) —
агент не отчитается «готово», не прогнав тесты. Разбиение задачи устроено сильнее: это не плоский
список шагов, а граф подзадач (`plan_write`) с зависимостями и исполняемыми критериями приёмки,
который выполняет `run_plan` — каждую подзадачу отдельным субагентом с чистым контекстом, с реальным
прогоном проверки и откатом при провале.
Плюс то, что особенно важно маленькой модели: карта кода (`repo_map`) и чтение по символу
(`read_symbol`) вместо чтения файлов целиком, хуки (форматтер/линтер сразу после правки),
откат правки командой `/undo`, точечные размышления и мини-бенчмарк в `bench/`.

```
› добавь поле active в модель User и выведи его в шаблоне
● plan_write(3 подзадач)
  план: 0/3
  ☐ n1  добавить поле active в models.User  → models.py
  ☐ n2  показать active в render            ← n1
  ☐ n3  обновить тесты вида                 ← n2
● run_plan(выполнить план)
  ▶ n1  добавить поле active в models.User
    ● read_symbol(User)
    ● edit_file(models.py)
    ↳ субагент завершён (4 запроса)
  ☑ n1  приёмка пройдена
  ▶ n2  показать active в render
    ● edit_file(views.py)
    ↳ субагент завершён (5 запросов)
  ☑ n2  приёмка пройдена
  ⎿ Исполнение плана: 3/3 подзадач готово · субагентов 3 · откатов 0 · 96.4s
● run_tests()
  ⎿ 12 passed [tests PASSED: 12 passed · exit code 0]
```

## Установка

### Вариант A: llama.cpp (рекомендуется)

```bash
brew install llama.cpp
bin/llama.sh                    # qwen3.5:4b с Hugging Face, контекст 16k, KV-кэш q8_0 — держите окно открытым
# в другом терминале:
loca --backend llamacpp         # или "backend": "llamacpp" в ~/.loca/config.json
```

Свой GGUF (например, дообученный): `bin/llama.sh ~/models/my-coder-v2-Q4_K_M.gguf`. Контекст и
модель задаются при запуске сервера — loca сам читает их из `/props`, поэтому `-m`/`--ctx` в loca
для этого бэкенда ни на что не влияют. Почему llama.cpp: та же основа, что у Ollama, но без
прослойки — все флаги под рукой (контекст, квантование KV-кэша, flash attention, слоты),
префикс промпта кэшируется сервером (`cache_prompt`), и работает любой GGUF без Modelfile.
Минус: одна модель на процесс — сменить модель = перезапустить `bin/llama.sh`.

### Вариант B: Ollama

```bash
# 1. Ollama
brew install ollama            # или приложение с ollama.com
# Настройки для 8 GB: KV-кэш в 8 бит и flash attention примерно вдвое уменьшают расход памяти на контекст
launchctl setenv OLLAMA_FLASH_ATTENTION 1
launchctl setenv OLLAMA_KV_CACHE_TYPE q8_0
launchctl setenv OLLAMA_MAX_LOADED_MODELS 1
# перезапустите Ollama после этого

# 2. Модель
ollama pull qwen3.5:9b          # по умолчанию (16 GB); на 8 GB: ollama pull qwen3.5:4b

# 3. Агент
cd loca
pipx install -e .              # или: python3 -m pip install -e .
loca                           # запуск в папке проекта
```

Без установки пакета можно положить обёртку в `~/.local/bin/loca` (пример — `bin/loca.sh` в
репозитории) и добавить эту папку в `PATH`:

```sh
#!/bin/sh
LOCA_REPO="${LOCA_REPO:-$HOME/Documents/loca}"
PYTHONPATH="$LOCA_REPO${PYTHONPATH:+:$PYTHONPATH}" exec "${LOCA_PYTHON:-python3}" -m loca "$@"
```

```zsh
# ~/.zshrc или ~/.oh-my-zsh/custom/loca.zsh
[[ ":$PATH:" != *":$HOME/.local/bin:"* ]] && export PATH="$HOME/.local/bin:$PATH"
```

Если не хотите устанавливать пакет, запускайте так: `python3 -m loca` (из папки `loca`, либо задайте `PYTHONPATH`).

## Какую модель выбрать на 8 GB

macOS сама занимает около 3 GB, так что модели остаётся примерно 4–5 GB, включая контекст.

| Модель | Вес | Для чего |
|---|---|---|
| `qwen3.5:9b` (**по умолчанию**) | ~6.6 GB | Заметно лучше держит план, инструменты и длинные правки. Нужно 16 GB, либо настройки из раздела ниже |
| `qwen3.5:4b` | ~3.4 GB | Выбор для 8 GB: нативные tools + thinking, гибридное внимание — контекст дешевле по памяти |
| `qwen3:4b` | ~2.5 GB | Запасной вариант, если 3.5 не влезает или тормозит |
| `qwen2.5-coder:3b` / `:7b` | 2 / 4.7 GB | Сильны в коде, но хуже держат агентный цикл; 7b — только с `--ctx 8192` и закрытым браузером. Отлично подходят для автодополнения в редакторе (Continue) |

На 8 GB ставьте `"model": "qwen3.5:4b"` в `~/.loca/config.json` (или запускайте `loca -m qwen3.5:4b`).

Честно о возможностях: модель на 4B параметров справляется с понятными задачами — найти место в коде,
поправить функцию, прогнать тесты, объяснить код. С большими рефакторингами на много файлов ей тяжело.
Помогает давать узкие, конкретные задачи. Режим размышлений (`/think` или `--think`) заметно повышает
качество, но в 2–4 раза замедляет ответы.

### Запуск на qwen3.5:9b (8 GB)

Модель весит 6.6 GB. По умолчанию macOS даёт видеопамяти только около 2/3 RAM (~5.3 GB), поэтому без
настройки часть слоёв уйдёт на CPU и всё сильно замедлится.

```bash
ollama pull qwen3.5:9b
# 8-битный KV-кэш и flash attention — примерно вдвое меньше памяти под контекст
launchctl setenv OLLAMA_FLASH_ATTENTION 1
launchctl setenv OLLAMA_KV_CACHE_TYPE q8_0
launchctl setenv OLLAMA_MAX_LOADED_MODELS 1   # перезапустите Ollama после этого
sudo sysctl iogpu.wired_limit_mb=6800         # сбрасывается после перезагрузки
# закройте браузер, IDE, Docker; автодополнение параллельно не запускайте
ollama ps                                     # в PROCESSOR должно быть "100% GPU"
```

Профиль под 8 GB — `~/.loca/config.json` (контекст 8k вместо 16k, короче `keep_alive`, раньше
сжатие, жёстче обрезка вывода инструментов):

```json
{
  "model": "qwen3.5:9b",
  "num_ctx": 8192,
  "keep_alive": "10m",
  "max_steps": 30,
  "subagent_max_steps": 12,
  "code_subagent_max_steps": 18,
  "compact_threshold": 0.7,
  "keep_recent_turns": 2,
  "max_tool_output": 5000,
  "old_tool_output": 400
}
```

8k контекста с `q8_0`-кэшем стоит примерно 0.5 GB поверх 6.6 GB весов — это потолок для 8 GB,
и запас там уже отрицательный. Если в `ollama ps` видно `CPU/GPU`, ответы идут единицами токенов в
секунду или Mac уходит в swap (Activity Monitor → Memory, жёлтая/красная Memory Pressure) —
вернитесь на `qwen3.5:4b`: `loca -m qwen3.5:4b` или `"model": "qwen3.5:4b"` в том же файле.
Разовый запуск с ещё меньшим контекстом: `loca --ctx 4096`.

## Использование

```bash
loca                          # диалог
loca "объясни структуру проекта"
loca -p "найди TODO в коде"   # один запрос без диалога (удобно в скриптах)
git diff | loca -p "напиши commit message"
loca -c                       # продолжить последнюю сессию в этой папке
loca --mode plan              # только чтение: агент исследует и предлагает план
loca --yolo                   # не спрашивать разрешений (опасные команды спросит всё равно)
loca -m qwen2.5-coder:7b --ctx 8192
```

### Команды внутри диалога

| | |
|---|---|
| `/init` | агент изучит проект и создаст `LOCA.md` — память о проекте |
| `#текст` | дописать заметку в `./LOCA.md` |
| `!команда` | выполнить shell-команду самому (модель увидит вывод) |
| `/mode default\|accept-edits\|plan\|yolo` | режим разрешений |
| `/model [имя]` | сменить модель / список моделей |
| `/think` | включить или выключить размышления |
| `/compact`, `/context` | сжать контекст / показать, сколько занято |
| `/plan-show` | текущий граф подзадач (то же — `/todos`, `/tasks`) |
| `/plan` | перейти в режим плана: только чтение, затем агент предложит план |
| `/test [цель]` | прогнать тесты самому (модель увидит результат) |
| `/vars [имя\|clear]` | переменные агента: список, значение, сброс |
| `/undo` | откатить последнюю правку файла (повторяется) |
| `/hooks` | какие хуки настроены |
| `/sessions`, `/resume <id>`, `/clear` | сессии |
| `/mcp` | статус MCP-серверов |
| `"""` | многострочный ввод (открыть и закрыть) |

Ctrl+C прерывает текущий ответ, Ctrl+D — выход.

### Разрешения

Когда агент запрашивает разрешение, можно ответить:

- `y` или Enter — разрешить;
- `a` — разрешить на всю сессию (правило вида `bash(npm test*)`);
- `n` — запретить;
- любой текст — запретить и передать модели указание, например «не удаляй, переименуй в .bak».

Что разрешается без вопросов:

- **всегда:** чтение, поиск и безопасные команды (`ls`, `git status`, `git diff` и т. п.);
- **в режиме accept-edits:** ещё и правки файлов внутри проекта;
- **в режиме yolo:** всё, кроме опасного — `sudo`, `rm -rf /`, `curl … | sh`, `git push --force`
  и записи за пределы проекта. На эти действия агент всегда спрашивает.

## Vim / Neovim

Плагин лежит в самом репозитории — `vim/plugin/loca.vim`. Подключение (одна строка в `~/.vimrc`,
либо укажите папку `loca/vim` менеджеру плагинов):

```vim
set runtimepath+=~/Documents/loca/vim
```

Готовый блок с настройками: `vim/vimrc.snippet` — можно дописать целиком:
`cat ~/Documents/loca/vim/vimrc.snippet >> ~/.vimrc`.

Вариант вообще без правки `~/.vimrc`: Vim сам сканирует `~/.vim/plugin/*.vim`, поэтому достаточно
положить туда загрузчик из репозитория — `cp ~/Documents/loca/vim/loader.vim ~/.vim/plugin/loca.vim`.
Он добавляет `loca/vim` в `runtimepath` и делает `source` плагина, так что правки в репозитории
подхватываются сразу, а отключается всё удалением одного файла.

Если `loca` не в `$PATH` терминала Vim, укажите путь: `let g:loca_cmd = '~/.local/bin/loca'`
(или `'python3 -m loca'`).

| Команда | Что делает |
|---|---|
| `:Loca [запрос]` | диалог с агентом в терминальном сплите, cwd — корень проекта (`accept-edits`, если запрос задан) |
| `:Loca! [запрос]` | то же в режиме `--yolo` |
| `:'<,'>Loca запрос` | добавляет к запросу ссылку на выделенные строки: <code>`src/utils.py:12-30` — запрос</code> |
| `:LocaAsk запрос` | быстрый ответ в отдельном буфере, правки запрещены (`-p --mode plan`) |
| `:LocaTest [цель]` | «прогони тесты и исправь падения» |
| `:LocaResume` | продолжить последнюю сессию в этой папке (`loca -c`) |
| `:LocaRoot` | показать, какой каталог плагин считает корнем проекта |

Привязки по умолчанию: `<leader>ll` (диалог; в visual — с выделением), `<leader>lp` (с запросом),
`<leader>la` (спросить), `<leader>lt` (тесты), `<leader>lr` (продолжить). Отключаются
`let g:loca_no_mappings = 1`.

Настройки: `g:loca_cmd` (по умолчанию `loca`; можно `python3 -m loca` или полный путь),
`g:loca_args` (добавляются всегда, например `['--think']`), `g:loca_split`
(`botright vertical` | `botright` | `tab`), `g:loca_size`, `g:loca_root` (принудительный корень).

**Корень проекта.** Плагин идёт от файла вверх до `.git` / `.loca` / манифеста (`pyproject.toml`,
`package.json`, `Cargo.toml`, `go.mod`, `Makefile`, `LOCA.md`…) и **никогда не поднимается выше
домашнего каталога**: иначе глобальный `~/.loca` делал корнем весь `$HOME`, и агент стартовал в
домашней папке вместо проекта. Перед запуском плагин печатает выбранный корень, `:LocaRoot` покажет
его в любой момент, а из терминального буфера (где файла нет) берётся последний найденный корень.

Выделенные строки не копируются в промпт — агент получает ссылку `path:12-30` и читает файл сам,
так что контекст не раздувается. Агент правит файлы на диске, поэтому плагин включает `autoread` и
делает `checktime` после выхода из терминала — открытые буферы обновляются сами.

## Настройка

`~/.loca/config.json` (глобально) и `.loca/config.json` (в проекте):

```json
{
  "model": "qwen3.5:9b",
  "num_ctx": 16384,
  "temperature": 0.2,
  "think": false,
  "permission_mode": "default",
  "test_command": "",
  "reminder_every": 6,
  "plan_min_nodes": 3,
  "plan_min_files": 2,
  "plan_max_attempts": 2,
  "max_plan_subagents": 12,
  "plan_rollback": true,
  "accept_timeout": 180,
  "vars_limit": 4000,
  "think_smart": true,
  "max_seconds": 0,
  "plan_gate_steps": 6,
  "plan_gate_files": 2,
  "trace_len": 60,
  "snapshots_keep": 200,
  "hooks": {"after_edit": ["ruff format {file}"], "stop": ["pytest -q"]},
  "allow": ["bash(npm test*)", "bash(pytest*)", "edit_file"],
  "deny":  ["bash(git push*)"],
  "mcp_servers": {
    "fs-docs": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/misha/docs"],
      "tools": ["read_text_file", "search_files"]
    }
  }
}
```

Все параметры с описаниями перечислены в `loca/config.py`. Для MCP советую ограничивать список
`tools`: описание каждого инструмента занимает место в небольшом контексте модели.

**Свои slash-команды** — это файлы `.loca/commands/<имя>.md` в проекте или `~/.loca/commands/`.
`$ARGUMENTS` заменяется текстом после команды. Пример — `.loca/commands/review.md`:

```
Сделай ревью изменений: запусти `git diff $ARGUMENTS`, найди баги и опиши их списком.
```

После этого можно вызывать `/review HEAD~1`.

**Память:** агент читает `~/.loca/LOCA.md`, а также `LOCA.md`, `AGENTS.md` или `CLAUDE.md` во всех папках
от корня git-репозитория до текущей.

## Архитектура

```
loca/
  cli.py          REPL, slash-команды, аргументы, headless-режим
  agent.py        агентный цикл, сжатие контекста, субагенты, защита от зацикливания
  plan.py         граф подзадач: разбор, валидация, готовность, отрисовка
  executor.py     исполнение плана: субагент на подзадачу, приёмка, откат
  llm.py          клиент Ollama /api/chat (стриминг) + разбор tool calls из текста
  permissions.py  режимы, правила allow/deny, безопасные и опасные команды, диалог подтверждения
  memory.py       LOCA.md / AGENTS.md, системные промпты
  session.py      сохранение и продолжение диалогов (~/.loca/sessions), включая переменные
  state.py        переменные сессии и подстановка {{имя}} в аргументы инструментов
  hooks.py        команды проекта вокруг действий агента (after_edit / after_tests / stop)
  snapshots.py    копии файлов перед правкой и откат (/undo)
  mcp.py          MCP-клиент (stdio JSON-RPC)
  tools/
    fs.py         read_file, write_file, edit_file, list_dir, glob, grep
    codemap.py    repo_map (карта символов), read_symbol (одно определение)
    shell.py      bash (cd сохраняется между вызовами, таймауты)
    agentic.py    plan_write (граф подзадач), run_plan, exit_plan_mode, task
    tests.py      run_tests (определяет pytest / npm / cargo / go / make)
    vars.py       set_var, get_var, del_var
    web.py        web_fetch
vim/plugin/loca.vim   команды :Loca, :LocaAsk, :LocaTest, :LocaResume
vim/loader.vim        загрузчик для ~/.vim/plugin/ (без правки ~/.vimrc)
vim/vimrc.snippet     блок для ~/.vimrc
bench/tasks.py        12 задач мини-бенчмарка
bench/run.py          раннер: прошло/шагов/токены/секунды, сравнение с baseline
```

**Цикл.** Запрос отправляется модели вместе со схемами инструментов. Агент выполняет вызванные
инструменты (с проверкой разрешений), возвращает модели результаты и повторяет, пока модель не даст
ответ без вызовов (лимит — `max_steps`).

**Что сделано специально под маленькие модели:**

- используется нативный API Ollama: только он позволяет задавать `num_ctx` и `think`;
- если модель напечатала вызов текстом (`<tool_call>{…}</tool_call>` или JSON-блоком), он всё равно распознаётся;
- аргументы приводятся к нужным типам (`"10"` → `10`), а ошибки возвращаются модели с подсказками:
  похожие имена файлов, ближайшие строки для `edit_file`;
- `edit_file` находит нужный фрагмент, даже если модель ошиблась в отступах, и сам их выравнивает;
- перед правкой файл обязательно нужно прочитать, а если он изменился на диске — прочитать заново.
  Сообщение об этом называет факты, а не правило: «'z/dilemma.py' ALREADY EXISTS (163 lines,
  4821 bytes) … Next call: read_file with path 'z/dilemma.py'» — иначе модель решает, что файла нет,
  и повторяет тот же `write_file`. Есть и законный выход: `write_file(..., overwrite=true)`, когда
  прежнее содержимое не важно;
- два одинаковых **провалившихся** вызова подряд — уже цикл: агент прямо говорит «не отправляйте
  это третий раз, сделайте то, что написано в ошибке, или смените подход»;
- сжатие контекста принимается только если контекст реально уменьшился. Пересказ может оказаться
  длиннее вырезанного куска (видели ~9.5k → ~11.4k), и тогда сжатие срабатывало каждый шаг, тратя
  вызов модели впустую; теперь такой результат откатывается, а повтор откладывается до реального
  роста контекста;
- после трёх одинаковых вызовов подряд агент подсказывает модели сменить подход;
- если модель вернула пустой ответ, агент один раз просит её продолжить;
- контекст сжимается в два этапа. При заполнении на 75 % сначала урезаются старые выводы инструментов,
  а если этого мало — старая часть диалога заменяется кратким пересказом. Сжатие включается только
  при необходимости, чтобы Ollama могла переиспользовать кэш промпта;
- субагенты (`task`) работают в отдельном контексте: `research` — только чтение, `code` — полный
  набор инструментов для самостоятельного куска работы. Переменные у них общие с основным агентом.

## Разбиение задачи, переменные и тесты

**Граф подзадач.** Для задачи из 3+ действий или 3+ файлов агент сначала вызывает `plan_write` и
описывает 2–7 подзадач. У каждой: что меняет (`files`), от чего зависит (`depends_on`) и —
обязательно — **исполняемая** приёмка:

```json
{"id": "n2", "title": "переписать store.py на validate_user",
 "files": ["store.py"], "depends_on": ["n1"],
 "accept": {"kind": "tests", "target": "tests/test_store.py"}}
```

Виды приёмки: `tests` (прогон тестов, можно `target` и `pattern`), `cmd` (любая команда, код
возврата 0) и `symbol` (в файле появилось определение). Текстовый критерий не принимается: его
некому проверить, а маленькая модель, оценивая собственную работу, почти всегда отвечает «да».
Подзадача без приёмки, висячая зависимость, цикл и повтор `id` — план не принимается, и модель
получает конкретное указание, что чинить.

**Исполнение.** `run_plan` берёт готовые по зависимостям подзадачи и для каждой:

1. Прогоняет приёмку **до** работы. Если она уже зелёная — критерий ничего не проверяет, подзадача
   блокируется, а планировщик получает замечание. (Тот же приём, что в бенчмарке: тест обязан
   падать на сломанном коде.)
2. Отдаёт подзадачу `code`-субагенту с чистым контекстом. В контракт кладётся только нужное:
   заголовок, список файлов, что уже сделали зависимые подзадачи, карта символов этих файлов и
   текст приёмки.
3. Запускает приёмку по-настоящему. Успех — статус `done`, результат в переменную (`result_var`).
4. Провал — правки подзадачи откатываются снимками, и субагент запускается заново с текстом ошибки
   (`plan_max_attempts`, по умолчанию 2). После последней попытки — откат, статус `failed` и
   возврат к планированию.
5. Если сломана сама проверка (нечем запускать, неверные флаги), попытки не тратятся: виноват план.

Цикл ведёт Python, а не модель: родитель вызывается на планирование и на разбор провала, а между
ними не участвует. Так контекст родителя не забивается выводом инструментов, а Ollama не
переоценивает его промпт после каждой подзадачи. Перепланирование — это повторный `plan_write`
целиком: подзадачи с теми же `id` и `title`, которые уже прошли приёмку, сохраняют статус и не
переделываются. Маленькие задачи (меньше `plan_min_nodes` подзадач или `plan_min_files` файлов)
`run_plan` не берёт — там делегирование дороже пользы. `/plan-show` — посмотреть граф самому,
каждые `reminder_every` шагов цикл напоминает модели про незакрытые подзадачи.

**Переменные.** `set_var("test_cmd", "python3 -m pytest -q")` сохраняет значение, после чего в любом
аргументе любого инструмента можно писать `{{test_cmd}}` — агент подставит текст перед вызовом.
Это дешевле, чем держать текст в контексте: переменные переживают сжатие контекста и сохраняются в
сессии, так что после `/resume` они на месте. В `content` у `write_file` и в `old_string`/`new_string`
у `edit_file` подстановка срабатывает только если весь аргумент — это ровно `{{имя}}`, поэтому шаблоны
с `{{...}}` внутри файлов не ломаются. `get_var`, `del_var` и `/vars` — для просмотра и очистки.

**Тесты.** `run_tests` сам находит команду: `pytest`, `npm`/`pnpm`/`yarn test`, `cargo test`,
`go test ./...`, `make test` (или `test_command` из конфига, или явный `command`). pytest выбирается
только если он есть у того же интерпретатора, которым запущен агент: после обновления питона (brew на
3.14, например) pytest остаётся у старого, и вместо «No module named pytest» берётся stdlib-unittest.
Исполнитель плана такую поломку отличает от провала работы и не откатывает правки субагента. Вывод сокращается
до сути с итогом вида `[tests PASSED: 12 passed · exit code 0]`. Если агент правил файлы и попытался
закончить, не прогнав тесты, цикл один раз вернёт его: «изменил код — прогони тесты, а если теста нет
— сначала напиши». Отдельно так же напоминается про незакрытые шаги плана. `run_tests` разрешён без
вопросов (`"allow": ["run_tests"]` в дефолтах).

**Режим плана.** `loca --mode plan` или `/plan`: правки запрещены, агент исследует код и вызывает
`exit_plan_mode` с планом. План показывается вам: `y` — принять (агент переключается в
`accept-edits` и начинает работать, план остаётся в `{{plan}}`), `n` или текст — вернуть на доработку.

## Задание перед работой и «сначала запусти»

Маленькая модель чаще ошибается не в коде, а в понимании просьбы: достраивает размытое
своими догадками и уверенно делает не то. Поэтому в диалоге перед задачей, которая
**меняет файлы** («добавь», «исправь», «переименуй», «вынеси»…), loca отдельным коротким
запросом без инструментов переписывает просьбу в задание и показывает его:

```
Понял задачу так:
Цель: добавить флаг --width в CLI, обрезать длинные ячейки
Файлы: app/cli.py, app/format.py, app/config.py
Ограничения: без флага вывод не меняется
Готово, когда: python3 -m unittest tests.test_cli
Предположения: ширина по умолчанию 8
Вопросы: обрезать с «…» или без?
Enter — выполнять · текст — поправить/ответить на вопросы · n — отмена
```

Задание строится по карте проекта (`repo_map`), поэтому пути в нём настоящие. Всё, чего
нет в просьбе, модель обязана записать в «Предположения», а не в цель. Ответ или поправка
пересобирают задание (до трёх раз); подтверждённое задание уходит агенту вместе с просьбой.
Вопросы («почему», «что делает», «объясни») подтверждения не требуют. `/spec auto|always|off`
или `"spec"` в конфиге; в `-p` и в бенчмарке шаг пропускается — подтверждать некому.

**Сначала запусти.** На вопросы «что выведет», «почему падает», «почему ошибка» модель
отвечает из головы плохо, а запуск не врёт. Такой вопрос получает напоминание: сначала
выполнить код (файл проекта, тесты или фрагмент из вопроса через `.loca/scratch/`),
потом объяснять механизм по реальному выводу. Отключается `"verify_first": false`.

## Приёмка промежуточных подзадач

Прогоны hard3 и Kaggle 19.10 показали одну причину провала планов: у каждой подзадачи
приёмка «весь набор тестов». Тесты описывают конечное состояние, поэтому промежуточная
подзадача честно делает свою часть, набор остаётся красным — и её верная правка
откатывается. Замечание в ответе `plan_write` модель игнорировала, поэтому теперь
`plan_write` сужает приёмку сам:

* весь набор остаётся только у последней подзадачи-«стока» (от неё никто не зависит);
* остальным — их собственный тест: тестовый файл из `files` или `tests/test_<модуль>.py`;
* если теста нет — `smoke`: файлы подзадачи **изменились** и компилируются.

И вторая половина: если субагент сделал больше своей части и приёмка следующей подзадачи
уже зелёная, это теперь `done` («уже выполнена предыдущими подзадачами»), а не `blocked`.
`blocked` за «зелёный до работы» остаётся только пока в плане ещё ничего не сделано —
тогда критерий действительно пустой.

Мелочи из тех же трасс: путь вида `/app/config.py` (такого корня нет) понимается как
`app/config.py` проекта, а `read_symbol("app.cli")` / `read_symbol("pkg.core.calc_total")`
понимают путь модуля в стиле import.

## Навигация по коду: repo_map и read_symbol

Маленькая модель обычно ошибается не в коде, а в поиске места: `read_file` на 400 строк съедает
контекст, хотя нужны были 20 строк одной функции.

- `repo_map` — дерево символов проекта: файлы, классы, функции, методы с номерами строк. Python
  разбирается через `ast`, остальные языки (js/ts, go, rust, java, sh…) — регулярками. `path` на
  файл даёт outline одного файла, `pattern` фильтрует по имени.
- `read_symbol` — одно определение целиком: `read_symbol("Agent.execute")`. После него файл считается
  прочитанным, так что `edit_file` работает сразу. Если имя встречается в нескольких файлах, агент
  получит список мест и повторит вызов с `path`.

В системном промпте порядок закреплён: `repo_map` → `read_symbol` → `grep` → и только потом
`read_file` целиком.

## Хуки

Команды проекта, которые loca запускает вокруг своих действий. В `config.json`:

```json
{
  "hooks": {
    "after_edit":  ["ruff format {file}", "ruff check --quiet {file}"],
    "after_tests": ["git --no-pager diff --stat"],
    "stop":        ["python3 -m pytest -q"]
  },
  "hook_timeout": 120
}
```

`{file}` подставляется путём изменённого файла. Вывод хука дописывается к результату инструмента,
то есть модель видит замечания линтера сразу после правки, а не через пять шагов. Если файл изменил
форматтер, loca обновляет отметку времени и пишет «файл изменён хуком — перечитайте» — иначе
следующий `edit_file` упёрся бы в «changed on disk». Хук `stop` выполняется, когда агент собирается
ответить: если он падает, агент один раз получает его вывод и продолжает работу. `/hooks` — показать
настроенные.

## Откат правок: /undo

Перед каждой правкой файл копируется в `~/.loca/snapshots/<сессия>/`, журнал лежит там же, поэтому
`/undo` работает и после `/resume`. Команда откатывает последнюю правку (файл, созданный агентом,
удаляется), обновляет состояние буфера чтения и сообщает модели, что правки больше нет — она не
станет молча делать её заново. Глубина истории — `snapshots_keep` (по умолчанию 200 правок).

## Бюджет хода и план-гейт

Две вещи, без которых слабая модель зависает на многофайловой задаче.

**Лимит времени.** `"max_seconds"` в конфиге или `--max-seconds N`: агент проверяет дедлайн перед
каждым шагом и останавливается сам, печатая состояние плана. Дедлайн наследуют субагенты и
исполнитель плана — он не берёт новую подзадачу, если время вышло, вместо того чтобы плодить
субагентов, которым уже некогда работать. По умолчанию 0 — без лимита.

**План-гейт.** Модель должна вызывать `plan_write` на больших задачах, но 4B про это забывает: в
первом прогоне на `hard` план не использовался ни разу, и обе многофайловые задачи упёрлись в
таймаут. После гейта план пошёл в дело (6, 2 и 4 субагента на трёх задачах), таймауты исчезли, а
результат вырос с 2/4 до 3/4 при 15/16 частичных целей.
Теперь агент требует план сам, в двух случаях:

- запрос выглядит многофайловым (три и больше путей, либо «везде / во всём проекте / everywhere»,
  либо «переименуй / вынеси / отрефактори» вместе с парой файлов) — напоминание уходит перед первым
  же обращением к модели;
- прошло `plan_gate_steps` шагов (по умолчанию 6), правились `plan_gate_files` файлов (2) и плана
  всё ещё нет — приходит требование остановиться и прислать `plan_write` с остатком работы.

Оба напоминания одноразовые: если работы осталось на одну правку, модель может так и ответить.

Отдельный счётчик ловит вторую крайность — планирование вместо работы. `plan_stats` считает принятые
и отклонённые планы, отказы `run_plan` (план мельче `plan_min_nodes`/`plan_min_files`), субагентов и
откаты; после четвёртого плана подряд без единой запущенной подзадачи модель получает прямое
указание либо вызвать `run_plan`, либо доделать руками. В отчёте бенчмарка это видно строкой
«планов 6 (отклонено 2), субагентов 2, отказов run_plan 3».

## Точечные размышления

`think` целиком включённый замедляет ответы в 2–4 раза, целиком выключенный роняет качество на
сложных шагах. По умолчанию `think_smart: true`: размышления включаются на первом шаге хода
(планирование) и после вывода инструмента с признаками проблемы (`tests FAILED`, `Traceback`,
`exit code`, `Error:`), в остальных случаях выключены. `/think` и `--think` по-прежнему включают их
глобально и имеют приоритет.

## Мини-бенчмарк

Без измерений «стало лучше» неотличимо от везения, поэтому в репозитории есть 16 задач на маленьких
проектах, в двух группах.

**`core` (12 задач)** — по одному-два файла: исправить падающий тест, добавить флаг в CLI,
переименовать функцию в трёх файлах, написать тест (проверяется, что он падает на сломанном коде),
реализовать функцию по докстрингу, вынести дубль, ответить на вопрос по коду.

**`hard` (4 задачи)** — 3+ связанных изменения в разных местах: провести параметр через конфиг,
логику и CLI; переименовать символ вместе с реэкспортом и тестами; вынести валидацию в новый модуль
и покрыть её тестом; починить два независимых бага, на которые опирается третий тест. Именно здесь
ломается плоский список шагов, поэтому у каждой такой задачи есть **частичные цели**: «прошло/не
прошло» на слабой модели почти всегда «не прошло» и ничего не говорит о прогрессе, а `3/5 целей`
против `1/5` — говорит.

```bash
python3 bench/run.py --verify-tasks          # проверить сами задачи, без модели
python3 bench/run.py                         # все задачи текущей моделью
python3 bench/run.py --tasks hard            # только многофайловые
python3 bench/run.py -m qwen3.5:9b --ctx 8192 --out runs/9b.json
python3 bench/run.py --baseline runs/9b.json --out runs/4b.json
python3 bench/run.py --tasks write_test --keep --show-output
python3 bench/run.py --only-failed runs/hard2.json   # перезапустить только упавшие
```

Состояние агента (сессии, снимки для `/undo`) живёт в отдельном временном каталоге, а не внутри
рабочей копии. Это не косметика: снимок хранит файл **до** правки, и проверка «старого имени в
проекте не осталось» падала на `.loca_home/snapshots/00001_core.py`, то есть заваливала
переименование, которое агент выполнил правильно. Проверки с рекурсивным `grep` дополнительно
исключают служебные каталоги.

Каждая задача выполняется в своей временной копии, агент запускается с `--yolo` и `--stats`, поэтому
считаются не только «прошло/не прошло», но и шаги, токены, время и частичные цели. Флаг `--stats FILE`
работает и сам по себе: `loca -p --stats s.json "..."` кладёт метрики прогона в JSON.

Метрики пишутся **после каждого шага**, а не в конце: убитый по таймауту прогон всё равно оставляет
шаги, токены, список правленых файлов, счётчик ошибочных вызовов и трассу последних 60 вызовов
инструментов. Раньше таймаут давал пустую строку `0/0 токенов` и никакой информации о причине.

Чтобы агента не убивали вслепую, раннер передаёт ему `--max-seconds` (жёсткий таймаут минус
`--margin`, по умолчанию 45 c): агент останавливается сам, проверки всё равно отрабатывают, а в
отчёте видно `остановлен по --max-seconds`. Для упавших задач печатается разбор: какие инструменты
и сколько раз вызывались, доля ошибок, использовался ли план и последние шесть вызовов.

```
hard_width_option  ✗    31    58210/2140  842.0   1/3
                     не достигнуто: format_row обрезает, флаг --width в CLI
                     вызовы: edit_file×18, read_file×12 · ошибок 15/34
                     больше трети вызовов — ошибки: агент буксовал, а не работал
                     план не использовался (plan_write не вызывался)
                     последние вызовы:
                       ✗ шаг 28 edit_file(app/format.py) → old_string not found in file
```

`--verify-tasks` проверяет сами задачи: до работы агента все `checks` и все частичные цели обязаны
падать, иначе задача пустая. Задачи с `unittest discover` включают `tests/__init__.py` — с Python 3.11
каталог тестов должен быть пакетом, иначе `discover` падает с `Start directory is not importable`.

## Идеи для развития

- отдельная модель для кода: `qwen2.5-coder` для реализации мелких блоков по точной спецификации
  (главный риск — вытеснение KV-кэша основной модели при переключении, мерить бенчмарком);
- `rich` или `prompt_toolkit` для красивого вывода markdown и автодополнения;
- переключение на MLX (`mlx_lm.server`) — на Apple Silicon он быстрее; понадобится адаптер
  к OpenAI-совместимому API в `llm.py`.
